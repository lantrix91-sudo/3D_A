# Координаты plant-twin

## Редактирование расположения

После обновления выполните `python manage.py migrate`. В админке зоны задайте
`size_x` (размер на восток) и `size_z` (размер на север) в метрах от её ЮЗ угла.
Габариты намеренно не выводятся из GLB: выступающие части модели не являются
плановыми границами здания. До заполнения обоих размеров перемещение запрещено.
Ограничивается origin оборудования: `0 ≤ pos_x ≤ size_x`, `0 ≤ pos_z ≤ size_z`.
Геометрические столкновения оборудования между собой не проверяются.

В режиме редактирования admin двигает оборудование в локальной плоскости зоны
на неизменной высоте `pos_y`. Смещение и поворот группы зоны учитываются Raycaster.
Шаг сетки по умолчанию 0.05 м, меняется в панели. Q/E поворачивают на ±15°,
Shift+Q/E — на ±90°. Esc откатывает текущий жест; «Отменить», смена выбора
или завершение редактирования откатывают несохранённое расположение.
PATCH передаёт только `pos_x = object.position.x`, `pos_z = -object.position.z`
и нормализованный `rotation_deg` в диапазоне [0, 360), с точностью 0.01 м / 0.1°.
Сохранение и запись EquipmentMoveLog выполняются одной транзакцией.

Единицы — метры. Начало плана (0,0) — юго-западный угол здания.
pos_x — на восток, pos_z — на север, pos_y — высота над полом.

```text
План / вид сверху                  Three.js / вид сверху

         север, pos_z (+)                  -Z (север)
                ^                              ^
                |                              |
                |                              |
SW (0,0) -------+----> pos_x (+)      (0,0,0) --+----> +X (восток)
                       восток                   |
                                                v +Z (юг)

Высота: pos_y -> +Y (из плоскости рисунка вверх).
```

Единственное преобразование оборудования из плана в сцену:

```js
object.position.set(item.pos.x, item.pos.y, -item.pos.z);
object.rotation.y = THREE.MathUtils.degToRad(item.rotation_deg);
```

Угол положителен против часовой стрелки при взгляде сверху. Ассет в нулевом
повороте смотрит дверцей на -X. Положение — origin ассета в центре основания.
Запасная коробка поднята внутри группы на половину высоты; корень остаётся на pos_y.
API возвращает исходные плановые координаты без инверсии Z.

## Зоны и фактический hall_v0.glb

Файл цеха не изменён. Проверенные границы исходного GLB:
X=[-91.246,0], Y=[-0.02,6], Z=[-3.350,81.243]. Это не совпадало с положительным
востоком и отрицательным Three.js Z. Пользователь разрешил повернуть **только модель
цеха на 180° вокруг Y**. В зоне main установлен `model_rotation_deg=180`.
Смещения зоны и её основной rotation_deg сохранены равными нулю.

```text
Zone group: offset(x, 0, -z), rotation_deg
  ├── hall GLB: model_rotation_deg = 180°
  ├── oven-1: (pos_x, pos_y, -pos_z), собственный rotation_deg
  └── остальные станки: такое же преобразование
```

Коррекция экспорта не применяется к станкам и их ассетам. После поворота границы
цеха X≈[0,91.246], Z≈[-81.243,3.350]; выступающие части геометрии могут выходить
за плановый прямоугольник. Пол, стены и оборудование не зеркалятся масштабом -1.
Для другой корректно экспортированной зоны оставляйте model_rotation_deg=0.

SHA-256 исходного hall_v0.glb:
`D7743A3E1F38DF849EC4C7FF0C0EE2015CF35437D5584F314CE1E6A9CFF734E7`.

## Привязка чертежа двойника к зоне

Сцена `frontend-twin` построена в координатах чертежа (`plant-layout.json`): ноль — пересечение осей 1 и А, X на восток, север — минус Z. Оборудование хранится в координатах зоны, поэтому их связывают три поля зоны:

| Поле | Значение |
|---|---|
| `plan_offset_x` | где на чертеже нуль зоны: метры на восток от оси 1 |
| `plan_offset_z` | где на чертеже нуль зоны: метры на север от оси А, к югу — отрицательное |
| `plan_rotation_deg` | поворот осей зоны относительно чертежа, против часовой стрелки при взгляде сверху |

```text
Сцена двойника = привязка(plan_offset, plan_rotation_deg) ∘ зона(offset, rotation_deg) ∘ (pos_x, pos_y, -pos_z)
```

Поля не меняют хранимые `pos_x`, `pos_z` и не влияют на `offset_*`, `rotation_deg`. Фронтенд применяет привязку при показе и обратное преобразование при сохранении (`planToWorld`, `worldToPlan`).

**Измерено для зоны `K_1` (Koktal_1):** `plan_offset_x = -0.68`, `plan_offset_z = -6.07`, поворот 0. Значения ставит миграция `plants.0005`, если они ещё не настроены; поправить можно в админке.

Метод: верхние грани стен `Koktal_1.glb` и стены чертежа растеризованы на сетке 2 см и совмещены взаимной корреляцией. Перебраны повороты на 0, 90, 180, 270° с зеркалом и без, малые повороты ±1,5° с шагом 0,1°, масштаб 0,994–1,006.

| Результат | Значение |
|---|---|
| Поворот, зеркало | нет: у 0° перекрытие 0,62, у остальных вариантов не больше 0,21 |
| Масштаб | 1: лучшая поправка 1,0005 даёт только 2–4 см на краях |
| Точность | около 0,05 м; в окнах 20×20 м поправка 0 ± 0,05 м, к востоку от x ≈ 70 м до 0,1 м |

Перекрытие 0,62 меньше единицы, потому что толщины стен в модели и на чертеже различаются. Прямоугольник пола GLB для такого измерения не подходит: он не совпадает с внешними стенами.

## Проверка

В data/ovens_import.json: 3 печи на pos_z=60.3 (X=19,22,25),
7 печей на pos_z=65.5 (X=19,22,25,28,31,34,37). В Three.js это Z=-60.3/-65.5.
Поскольку исходный файл расстановки не предоставлен, X заданы как демонстрационные
координаты с шагом 3 м. Их можно изменить в JSON или админке.
Первая группа повёрнута на 0°, вторая на 180°.

«Отладка» показывает оси в мировом нуле (X красная, Y зелёная, Z синяя), сетку
с шагом 1 м и плановые координаты четырёх углов Box3. «Вся сцена» рассчитывает
Box3 содержимого без сетки, переводит target в центр и подбирает расстояние.
