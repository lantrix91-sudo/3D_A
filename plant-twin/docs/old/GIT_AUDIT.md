## Перед первым публичным push

Обычный commit удаления GLB не удаляет их из предыдущих коммитов. Выберите один путь:

1. Опубликуйте чистый снимок исходников новым репозиторием без старой `.git`,
   перенося только проверенные исходники, docs и примеры окружения. Не копируйте
   `.env`, БД, media, data/GLB, `.venv`, node_modules и сборки. В этом случае пути
   Railway могут начинаться сразу с `/backend` и `/frontend`.
2. Если история нужна, сначала сохраните текущую работу локальным коммитом,
   создайте **отдельный локальный клон** и удалите GLB/data из истории в нём
   инструментом `git-filter-repo`. Не переписывайте рабочий репозиторий с
   несохранёнными изменениями. В фильтрах учитывайте исторические пути как
   `plant-twin/data/`, так и `data/`, и все `*.glb`. Затем повторите аудит.

Если при дополнительной проверке найден реальный секрет в старом коммите,
его следует заменить у провайдера/в приложении: одного удаления из Git недостаточно.

## Контроль перед коммитом

Из корня приложения:

```powershell
git status --short
git diff --cached --stat
git ls-files -- .env backend/.env backend/db.sqlite3 backend/media data
git check-ignore backend/.env backend/db.sqlite3 backend/media/example.glb data/hall_v0.glb frontend/node_modules frontend/dist
```

`git ls-files` не должен показывать приватные файлы; допустимы только намеренно
подготовленные `data/*.example`. Не используйте `git add -f` для игнорируемых файлов.
Перед публикацией проверьте содержимое staged diff, включая изменения, которые
уже были в рабочем дереве до подготовки деплоя.
