Аудит выполнен без изменения исходников, коммитов, публикации и обращения к production. Единственный добавленный документ — этот отчёт. Перед проверкой прочитаны документация `docs/`, корневой README, README mobile, simulator и backend-модулей. Сборки обновили игнорируемые артефакты `dist`.

Оценки трудозатрат ориентировочные, включают исправление и целевые регрессионные тесты; 1 день — рабочий день одного разработчика.

## Состояния оборудования: что совпадает, а что нет

- Источник истины для `condition` — backend. При fault из осмотра working/idle переходят в faulty; repair/maintenance/faulty сохраняются с записью отметки. Повторное состояние не должно обновлять момент фактической смены. В `rounds/services.py:268` поиск последней смены исключает события `previous_condition == condition`; защита от устаревшего осмотра тем самым не блокируется простой отметкой. Существующие тесты этих сценариев проходят.
- Mobile определяет итог чек-листа по наиболее тяжёлому ответу; backend повторяет расчёт независимо от присланного результата. Frontend показывает серверное состояние, а не реализует вторую конкурирующую машину переходов. Независимой несовместимой схемы переходов трёх клиентов не обнаружено.
- Практические расхождения связаны с датой/очередью, неполным чек-листом и отображением ошибок (№4, 9, 14, 24), а не с правилом fault → faulty.
- В `backend/equipment/conditions.py:68` карточка возвращает сохранённый telemetry status, тогда как план использует effective_status. Между истечением таймаута и очередным проходом watchdog возможен короткий разный статус карточки/плана. Не отнесено к серьёзным нарушениям: watchdog предусмотрен, фактическая задержка в production не измерялась.

## Дополнительные выводы по надёжности и размеру

- Истёкший токен сам по себе **не удаляет очередь**: 401 прекращает синхронизацию; 400/403/404 оставляют запись с error. Ошибки сети сохраняют запись. Главные риски — смена владельца/сервера, редактирование и неверное подтверждение отправки, а не обычный повтор того же UUID.
- Фото отправляются одним multipart-запросом с осмотром. Отдельной частично подтверждённой очереди фото нет. DB atomic защищает записи, но не физические файлы (№7); таймаут после принятия запроса предполагает повтор того же client_id.
- Не каждый catch — потеря данных: сбои WS в backend логируются, многие catch для необязательных cache/JSON fallback намеренные. Опасные исключения — молчаливое сохранение черновика (№8), успешный HTTP без корректного подтверждения (№12), а также необработанные ошибки ввода (№13).
- Индексы уже есть на UUID, дате обхода, inspected_at, equipment+inspected_at и signal+ts; FK также индексируются. Поэтому общего утверждения «индексов нет» нет. Требуют замера выборка истории условий и рост today, №18.
- Размер mobile приемлем для текущего состава, three.js туда не попал. Большой frontend chunk объясняется 3D-движком; lazy-load сцены имеет смысл для ускорения входа, но сам warning 500 КБ не является неисправностью. Графики уже выделены отдельно.
- Полные ответы содержат URL фото, не сами изображения. Главный риск объёма — число загружаемых записей и оригинальных изображений, а не сериализация бинарных данных в JSON. Реальные размеры пользовательских фото и базы production не измерялись.
- Прямые зависимости закреплены; `pip check` проходит. Gunicorn — документированная HTTP-альтернатива Daphne, его наличие не сочтено мёртвым кодом. README модулей-заготовок не означают существующих API. Больших гарантированно неиспользуемых зависимостей не подтверждено.
