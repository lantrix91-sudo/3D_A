# Фронтенд: объяснение для бэкендера

Действующий 3D-интерфейс — `plant-twin/frontend-twin/`, а не удалённый `frontend/`. Ниже пути относительно `frontend-twin/src/`, если не сказано иное.

## Что происходит при открытии страницы

1. `index.html` подключает `main.tsx`. Он очищает старые ключи демо из localStorage, применяет тему и монтирует React App в элемент root.
2. `App.tsx` вызывает `telemetryHub.initApp()`. Защита initialized не даёт повторить запуск. Сцена загружается отдельно через lazy/Suspense.
3. `serverHub.bootServerMode()` пытается восстановить вход через refresh JWT. Нет токена — LoginScreen. Нет сети — пустой основной экран с предупреждением и повтором через 5 секунд; фиктивные станки не создаются.
4. После входа `openPlan()` параллельно получает `/auth/me/` и `/plan/`. В useServer сохраняет имя, роли и права редактирования.
5. `replaceEquipment()` наполняет реестр из активных станков видимых зон плана. `planMapper` переводит серверные координаты/размеры в формат сцены. Переключателя скрытых зон пока нет.
6. `prepareServerRuntime()` создаёт хранилище в памяти, загружает настройки, очищает временную расстановку. Положение берётся с сервера.
7. Асинхронно загружаются стены первой видимой зоны и, для admin, каталог ассетов. Открывается WebSocket. snapshot даёт определения сигналов и значения; update обновляет отдельный станок.
8. Каждые 5 секунд checkStale пересчитывает устаревание. Графики отдельно запрашивают `/equipment/{code}/readings/`, запрос на станок кэшируется на 30 секунд.

React-компонент можно понимать как функцию, строящую участок экрана по текущим данным. Zustand store — общий объект состояния с подписками: его изменение вызывает перерисовку зависимых компонентов. Three.js рисует сцену, React Three Fiber позволяет описывать её React-компонентами, Drei даёт готовые камеры и вспомогательные элементы.

## Где данные живут

| Хранилище | Содержимое | Переживает перезагрузку |
|---|---|---|
| `store/appStore.ts` / useApp | Выбор, панели, временная расстановка, live, события, пустые журналы | Только то, что отдельно сохраняет settings |
| `store/serverStore.ts` / useServer | Пользователь, роли, права, зоны, типы, ассеты, состояние соединения | Нет |
| `domain/config.ts` | Массивы EQUIPMENT/SENSORS, словари по ID и счётчик useRegistry | Нет, наполняется из API |
| Локальные Map в serverHub | Последние WS-записи, live-состояния, кэш графиков и очереди сохранения позиций | Нет |
| `storage/memoryRepository.ts` | События, заготовки поломок/ППР, meta | Нет |
| `storage/settings.ts` | Тема/панели/настройки сцены через localStorage; сохранённые позы при старте очищаются | Да, кроме очищаемой расстановки |
| `storage/wallsCache.ts` | IndexedDB-кэш синхронизации стен | Да |
| `api/client.ts` | access в памяти, refresh в localStorage | Только refresh |

Не путать ленту EventFeed с ConditionEvent в Django: лента формируется из наблюдаемых клиентом переходов статуса и действий пользователя и исчезает при перезагрузке. Серверная история технического состояния существует отдельно, новый 3D-интерфейс её пока не читает.

## Как идут запросы

`api/client.ts` оборачивает fetch. При 401 выполняет refresh и один повтор; сетевые ошибки не должны удалять refresh. URL берётся из `api/config.ts`:

- dev: API_URL пустой, `/api`, `/media`, `/ws`, `/admin`, `/static` проходят через Vite proxy на VITE_BACKEND_URL;
- build: используется VITE_API_URL, WebSocket — VITE_WS_URL или адрес, выведенный из API_URL;
- VITE_STALE_SECONDS удалён: локальный расчёт offline использует last_seen + offline_seconds из plan/WS.

На сервере порог по умолчанию 180 секунд и может зависеть от типа; браузер использует переданное сервером значение и не требует Redis/watchdog для локального устаревания. Все VITE_* видны браузеру: секреты туда не помещать.

Перемещение: сцена → временный `settings.layout` → `commitServerPose()` → `worldToPlan()` → PATCH оборудования → обновление реестра. Запросы одного станка идут последовательно; при ошибке позиция откатывается. Сервер проверяет admin независимо от кнопок клиента.

Стены: редактор → walls.commit/persist → wallsSync → PUT с base_version. При 409 нужно выбрать серверную или свою версию. В отличие от положения станков, здесь реализован контроль конкурирующих правок.

## Реальные данные и остатки прототипа

| Область | Текущее происхождение |
|---|---|
| Список станков, названия, тип, координаты, размеры, condition | `/plan/`, ответы записи оборудования |
| Значения и метаданные сигналов, status | WebSocket; до его открытия — только статус из плана |
| Графики | HTTP readings, без искусственной генерации |
| Модели оборудования | Asset.url с сервера; при отсутствии — условная геометрия |
| Стены/колонны | Серверная версия, если есть; исходный чертёж как fallback |
| Оси, помещения, подложка, высота, подпись чертежа | Встроенный `domain/plant-layout.json` и ресурсы сцены, привязанные к конкретному проекту |
| Полные паспорта, документы, фото, история condition | API существует, но 3D-карточка его не вызывает |
| Обходы | Бэкенд и mobile реализуют; новый 3D-клиент не вызывает API routes/today и игнорирует WS inspection/route_changed |
| Поломки/ППР | Серверных моделей нет, JOURNALS_WRITABLE=false, списки пустые |
| Лента событий | Память текущей вкладки, не постоянный серверный журнал |
| Встроенные GLB/локальный импорт моделей | Остались в models3d; mapper не назначает builtinModel, вызовы локального импорта в текущем UI не найдены |
| Деморежим | Переключатель/генератор в цепочке запуска не найден; осталась очистка старого localStorage и отдельный Python simulator |

`idb` и `recharts` не являются доказанно лишними: используются кэшем стен и графиками. Название alarmEngine само по себе не означает оставшийся симулятор. Старые tools/e2e_* требуют пересмотра: часть ожидает demo-banner и старый порт 4173.

## Уже существующий мобильный клиент

`plant-twin/mobile/src/main.js` координирует экраны настроек, входа, маршрутов, шагов, осмотра и оборудования. `api/client.js` — JWT и multipart; `api/server.js` — адрес сервера. `offline/queue.js` хранит осмотры и фото в IndexedDB, `drafts.js` — незаконченный осмотр, `images.js` — изображения. `pwa/sw.js` кэширует оболочку; Vite формирует версию service worker при сборке. Capacitor Camera/App обслуживают Android и восстановление после камеры.

Список маршрутов/последние ответы также кэшируются в localStorage. Очередь повторяется каждые 30 секунд и при online; маршрут обновляется каждые 5 минут. Ошибки 400/403/404 помечают запись как требующую вмешательства, 0/401 приостанавливают отправку. После 48 часов backend осмотр не принимает. Привязки очереди к пользователю/серверу сейчас нет — [критичный пункт аудита](AUDIT.md#критично).
