# Телеметрия: приём данных и живой статус

Этап 3. Устройства (пока только симулятор) присылают измерения по HTTP, сервер
пишет историю, считает статус оборудования и рассылает его в браузер по WebSocket.
SCADA, PLC и внешние базы не подключены. Команды на устройства не отправляются.

```
устройство / симулятор ──POST /api/v1/readings/──▶ ingest() ──▶ Reading, Signal, Equipment.status
                                                      │
                                                      └─▶ Channels group "telemetry" ──▶ /ws/v1/live/ ──▶ 3D-сцена
check_offline (фон) ─────────────────────────────────────┘ (offline по таймауту)
```

Все источники данных (HTTP, будущие коллекторы MQTT/OPC UA/Modbus) вызывают
одну функцию `equipment.ingest.ingest(device_id, values, ts=None, seq=None, faults=None, source=...)`.

## Модель данных

| Где | Что |
| --- | --- |
| `Equipment.device_id` | ID устройства в пакетах. Назначается только в админке. |
| `EquipmentType.signal_templates` | Набор сигналов типа: `key`, `name`, `unit`, `kind` (`state`, `number` или `bool`). Сигналы создаются автоматически при создании оборудования. Новые шаблоны, сохранённые в админке, добавляются уже существующему оборудованию этого типа. |
| `Signal.device_key` | Ключ значения в пакете. По умолчанию совпадает с `key`; его можно переименовать под прошивку. |
| `EquipmentType.status_rules` | Правила статуса (см. ниже). |
| `EquipmentType.offline_seconds` | Таймаут offline для типа; если пусто, используется `STATUS_OFFLINE_SECONDS`. |
| `Reading` | История: значение пишется при изменении или не реже раза в `READING_MIN_INTERVAL_SECONDS` (30 с) на сигнал. |
| `DeviceKey` | Ключи устройств (хранится только SHA-256). |
| `IngestPacket` | Журнал дедупликации. Записи старше 7 суток удаляет `check_offline`. |

## POST /api/v1/readings/

Заголовки:

```
Content-Type: application/json
X-Device-Key: ptd_...
```

JWT пользователя для этого запроса не нужен и не используется.

### Одиночный пакет

```json
{
  "device_id": "oven-plc-01",
  "ts": 1792665651.25,
  "seq": 1042,
  "values": {"state": "run", "power": 41.7, "temperature": 212.4},
  "faults": ["temperature"]
}
```

| Поле | Обяз. | Описание |
| --- | --- | --- |
| `device_id` | да | `Equipment.device_id`. |
| `ts` | нет | Unix-время в секундах UTC, допускаются дробные. Если не указано, берётся время приёма. Допустимый диапазон: не более чем на 5 минут в будущем и не старше 7 суток. |
| `seq` | нет | Неотрицательный счётчик пакетов для дедупликации. Должен расти и после перезагрузки устройства: храните его в энергонезависимой памяти или начинайте со времени в мс. |
| `values` | да* | `{device_key: значение}`. Можно не передавать, если передан непустой `faults`. |
| `faults` | нет | Ключи сигналов с неисправным датчиком. |

Значения по `kind` сигнала:

- `number` — конечное число;
- `bool` — `true`/`false` или `0`/`1`;
- `state` — строка до 64 символов (`"run"`) или целое число (код состояния).

Ответ `201` для нового пакета и `200` для повторного:

```json
{"equipment": "oven-1", "duplicate": false, "status": "run", "written": 3}
```

`written` — сколько строк истории записано (неизменные значения чаще 30 с не пишутся).

### Пакет записей (досылка буфера)

```json
{
  "device_id": "oven-plc-01",
  "readings": [
    {"ts": 1792665600, "seq": 1001, "values": {"state": "stop", "power": 0.4}},
    {"ts": 1792665605, "seq": 1002, "values": {"power": 0.5}, "faults": ["temperature"]}
  ]
}
```

- В одном запросе от 1 до 500 записей; поля каждой записи такие же, как у одиночного пакета (без `device_id`).
- Пакет принимается целиком или отклоняется целиком: при ошибке в любой записи не сохраняется ничего, а в сообщении указан номер записи (`readings[3]: ...`). Перед отправкой устройство должно отбросить записи старше 7 суток.
- Записи обрабатываются по возрастанию `ts`. Прошлые данные попадают в историю, но не откатывают текущий статус и последние значения.
- На всё оборудование из пакета рассылается одно событие WebSocket.

Ответ (`201`, если принята хотя бы одна запись, иначе `200`):

```json
{"equipment": "oven-1", "accepted": 1, "duplicates": 1, "status": "run",
 "results": [{"index": 0, "duplicate": true}, {"index": 1, "duplicate": false}]}
```

### Идемпотентность

Повторная доставка не создаёт дублей. Если в пакете есть `seq`, ключом служит
`(device_id, seq)`, иначе `(device_id, ts)`. На дубль сервер отвечает `200` с
`"duplicate": true`, поэтому устройство может смело повторять отправку после таймаута.

### Ошибки

Тело ошибки: `{"error": {"code": "...", "message": "понятный текст"}}`.

| HTTP | `code` | Когда |
| --- | --- | --- |
| 400 | `invalid_format` | Не JSON-объект, нет `device_id`, неверный тип `ts`/`seq`/`faults`/`values`, лишние поля, пустой `readings`. |
| 400 | `invalid_value` | Значение не подходит под `kind` сигнала (строка вместо числа, `5` для bool, NaN). |
| 400 | `unknown_signal` | Ключа нет у оборудования. В сообщении перечислены доступные ключи. |
| 400 | `ts_out_of_range` | `ts` в будущем более чем на 5 минут или старше 7 суток. |
| 400 | `batch_too_large` | Больше 500 записей. |
| 401 | `device_key_missing` | Нет заголовка `X-Device-Key`. |
| 401 | `device_key_invalid` | Ключ неверен, отозван или выдан другому устройству. |
| 404 | `unknown_device` | `device_id` не привязан к оборудованию. |

## Ключи устройств

Ключ привязан к оборудованию. Сервер хранит только SHA-256 и первые 12 символов
(префикс для поиска в списке).

**В админке:** «Ключи устройств» → «Добавить» → выберите оборудование (у него
должен быть `device_id`) → «Сохранить». Ключ вида `ptd_...` один раз
показывается в жёлтом сообщении. Скопируйте его сразу: повторно он не
отображается. Чтобы отозвать ключ, выделите его в списке и выберите действие
«Отозвать выбранные ключи». Удалять ключи нельзя: отзыв сохраняет историю.
У одного устройства может быть несколько действующих ключей, это удобно для
плавной замены.

**Командой** (удобно для симулятора):

```bash
python manage.py issue_device_key oven-plc-01 --name "контроллер печи 1"
python manage.py issue_device_key --all --name simulator > sim-keys.json   # все устройства, JSON device_id → ключ
```

Не храните `sim-keys.json` в git.

Для локальной разработки `ALLOW_UNAUTHENTICATED_DEVICES=true` разрешает запросы
без заголовка. Неверный ключ при этом всё равно отклоняется. При `DEBUG=false`
этот флаг не даст запустить сервер.

## Статус оборудования

Возможные значения: `run`, `stop`, `alarm`, `offline`, `unknown`.

1. Если данных ещё не было → `unknown`.
2. Если свежих данных нет дольше `offline_seconds` типа (или `STATUS_OFFLINE_SECONDS`, по умолчанию 180) → `offline`.
3. Если сработало любое условие `alarm_if` → `alarm`.
4. Если есть state-сигнал со значением, значение переводится в статус по `state_map`. Значение не из карты даёт `unknown`.
5. Если state-сигнала нет, применяется `run_if`: все условия истинны → `run`, иначе `stop`.
6. Иначе → `unknown`.

Сигналы из `faults` (неисправный датчик) в правилах не участвуют, как будто значения нет.

Формат `status_rules` (все поля необязательны, пустой объект `{}` тоже допустим):

```json
{
  "state_signal": "state",
  "state_map": {"3": "alarm", "idle": "stop"},
  "alarm_if": [{"signal": "temperature", "op": ">", "value": 300}],
  "run_if": [{"signal": "power", "op": ">", "value": 0.5}]
}
```

- `state_signal` — ключ сигнала состояния. По умолчанию первый сигнал с `kind: state`.
- `state_map` дополняет общую карту `run/stop/alarm`, `1→run`, `0→stop`, `2→alarm`, `true→run`, `false→stop`.
- `op` — одна из операций `>`, `>=`, `<`, `<=`, `==`, `!=`. `signal` — это `key` сигнала, а не `device_key`.

Правила хранятся в данных типа. В коде нет ничего, что относилось бы к конкретному типу оборудования.

### Таймаут offline

`python manage.py check_offline` переводит оборудование без свежих данных в
`offline`, рассылает событие и чистит журнал дедупликации. В `start.sh` команда
запущена в фоне: `check_offline --loop $STATUS_CHECK_INTERVAL` (по умолчанию
15 с). Локально её запускают так:

```bash
python manage.py check_offline --loop 15
```

План и WebSocket-снимок показывают `offline` по таймауту и без watchdog. Watchdog
нужен, чтобы уже открытые браузеры получили событие.

## WebSocket /ws/v1/live/?token=<access JWT>

Подключаться могут только пользователи с ролью operator, engineer или admin.
Причина закрытия передаётся кодом:

| Код | Причина | Что делает клиент |
| --- | --- | --- |
| 4401 | Нет токена, токен неверен или истёк (проверка и при подключении, и на каждом событии) | Обновляет токен и переподключается. |
| 4403 | Нет роли | Не переподключается. |

Сообщения сервера:

```json
{"type": "snapshot", "equipment": [
  {"equipment": "oven-1", "status": "run", "ts": 1792665651.25,
   "values": {"state": "run", "power": 41.7, "temperature": 212.4},
   "faults": [], "signals": {"power": {"name": "Мощность", "unit": "кВт", "kind": "number"}}}
]}
{"type": "update", "equipment": "oven-1", "status": "alarm", "values": {...}, "faults": ["temperature"], "signals": {...}, "ts": 1792665656.0}
```

`equipment` — это код оборудования, `ts` — Unix-время последних данных. Клиент
может отправлять `{"type": "ping"}` и получать в ответ `{"type": "pong"}`.

Channel layer: если задан `REDIS_URL`, используется Redis, иначе InMemory. InMemory
работает только при `DEBUG=true` и в одном процессе, поэтому `check_offline` из
отдельного процесса доставит события только через Redis.

## Frontend

`src/api/live.js` подключается после загрузки плана. Переподключение идёт с
задержкой 1, 2, 4 … 30 с, ping каждые 25 с. При коде 4401 клиент обновляет
токен. Светодиод (`led_node_name`) и корпус окрашиваются по `COLORS` из
`src/scene/colors.js`: run — зелёный, stop — жёлтый, alarm — красный,
offline и unknown — серые. Корпус GLB подсвечивается, текстуры сохраняются.
Запасная коробка красится целиком. В панели выбранного оборудования видны
значения сигналов с единицами, «ошибка датчика» и время последних данных.
Плашка «Нет связи» в шапке означает, что WebSocket оборван и цвета могут быть
устаревшими.

## Симулятор и живые цвета

```bash
# 1. Backend (DEBUG=true, REDIS_URL пуст → InMemory)
cd backend
python manage.py migrate
#    в админке задайте device_id оборудованию (например oven-01, oven-02)
python manage.py issue_device_key --all --name simulator > ../simulator/sim-keys.json
python manage.py runserver            # daphne в INSTALLED_APPS → ASGI с WebSocket
python manage.py check_offline --loop 15     # второй терминал

# 2. Frontend
cd frontend && npm run dev            # http://localhost:5173, /ws проксируется на :8000

# 3. Симулятор (только стандартная библиотека Python)
python simulator/simulate.py --devices oven-01,oven-02 --keys-file simulator/sim-keys.json --interval 3
```

Войдите в интерфейс. Светодиоды начнут менять цвет, а в карточке выбранной печи
будут обновляться значения.

Режимы симулятора (`python simulator/simulate.py --help`):

| Проверка | Флаги |
| --- | --- |
| Устройства из плана | `--username admin --password ...` (нужен staff: только ему план отдаёт `device_id`) вместо `--devices` |
| Offline | `--stop-device oven-02 --stop-after 30`: через 30 с устройство замолкает, через `STATUS_OFFLINE_SECONDS` оно станет серым |
| Неисправность датчика | `--fault-rate 0.2`: в 20 % пакетов один числовой сигнал помечен в `faults` |
| Потеря пакетов | `--drop-rate 0.1`: `seq` растёт, но пакет не отправляется |
| Досылка буфера | `--outage-device oven-01 --outage-after 20 --outage-length 60`: минуту пакеты копятся, затем уходят одним пакетом записей с исходными `ts` и `seq` |
| Свой набор сигналов | `--signals "state:state,rpm:number:0:3000,door:bool"` |

Ключи можно также передать через `--keys '{"oven-01":"ptd_..."}'` или переменную
окружения `DEVICE_API_KEYS`. Если сервер недоступен, симулятор копит пакеты и
досылает их после восстановления связи.

## Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `STATUS_OFFLINE_SECONDS` | 180 | Таймаут offline (тип может переопределить). |
| `STATUS_CHECK_INTERVAL` | 15 | Период `check_offline` в `start.sh`. |
| `READING_MIN_INTERVAL_SECONDS` | 30 | Как часто писать в историю неизменное значение. |
| `ALLOW_UNAUTHENTICATED_DEVICES` | false | Приём без ключа, только при DEBUG. |
| `REDIS_URL` | пусто | Channel layer; обязателен при DEBUG=false. |
